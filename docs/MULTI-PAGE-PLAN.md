# برنامهٔ سایت‌های چندصفحه‌ای

تاریخ: ۸ سپتامبر ۲۰۲۶

## هدف و دامنه

هر سایت یک صفحهٔ اصلی ثابت و چند صفحهٔ مستقل داشته باشد. صفحهٔ مستقل می‌تواند از نوع «صفحهٔ عمومی»، «خدمت» یا «موضوع» باشد؛ هر سه از ویرایشگر بخش‌ها، قالب و هویت بصری مشترک سایت استفاده می‌کنند. مالک باید عنوان، آدرس، محتوای بخش‌ها، SEO و فعال‌بودن هر صفحه را مدیریت کند و محل و ترتیب لینک‌های منوی بالا و پایین سایت را انتخاب کند. کارت خدمت یا موضوع و دکمهٔ بخش نیز باید بتوانند به یک صفحهٔ داخلی وصل شوند.

## تصمیم‌های محصول و قرارداد

- صفحهٔ اصلی و URLهای فعلی حفظ می‌شوند. مسیر صفحهٔ مستقل `/s/:siteSlug/:pageSlug` و روی دامنهٔ تأییدشده `/:pageSlug` است. مقاله‌ها همچنان زیر `/blog/:postSlug` قرار دارند.
- آدرس صفحه یک قطعهٔ کوتاه انگلیسی با حروف کوچک، عدد و خط تیره است. آدرس تکراری در همان سایت و نام‌های رزروشده پذیرفته نمی‌شوند. ویرایش آدرس، لینک‌های داخلی مبتنی بر شناسه را نمی‌شکند؛ آدرس قدیمی پس از انتشار ۴۰۴ می‌شود. انتقال خودکار آدرس قدیمی در این مرحله نیست و در رابط توضیح داده می‌شود.
- `SiteContent.pages?: SitePage[]` به JSON پیش‌نویس اضافه می‌شود. `SitePage` شامل `id`, `title`, `slug`, `kind: page|service|topic`, `enabled`, `sections`, `seo` است. برند و قالب متعلق به کل سایت‌اند و در هر صفحه تکثیر نمی‌شوند.
- `SiteContent.navigation?: {header: NavigationItem[], footer: NavigationItem[]}` منوی سایت را مشخص می‌کند. هر آیتم `id`, `label`, `target` دارد. مقصد یکی از `home`، `page` با `pageId`، `section` با `sectionId` در صفحهٔ اصلی، یا `url` است. ترتیب آرایه ترتیب نمایش است. نبود navigation در دادهٔ قدیمی به معنی حفظ منوی خودکار فعلی است؛ آرایهٔ خالی انتخاب صریح مالک برای منوی خالی است.
- `Section.buttonPageId` و `SectionItem.pageId` مقصد داخلی پایدارند؛ هم‌زمان با URL مستقیم استفاده نمی‌شوند. انتخاب صفحه در ویرایشگر و ساخت صفحه از کارت خدمت/موضوع، نوشتن دستی URL را ضروری نمی‌کند.
- فعال‌بودن صفحه با قرارگرفتن در منو متفاوت است: صفحهٔ فعال می‌تواند فقط با لینک مستقیم باز شود. صفحهٔ غیرفعال پس از انتشار از پاسخ عمومی، مسیرها و لینک‌های داخلی حذف می‌شود؛ دادهٔ آن در پیش‌نویس باقی می‌ماند. حذف صفحه لینک‌های وابسته را از پیش‌نویس پاک می‌کند.
- ذخیره و انتشار برای مجموعهٔ سایت انجام می‌شود: صفحه‌ها، منوها، برند، صفحهٔ اصلی و SEO در همان snapshot مستقل منتشر می‌شوند. حذف یا تغییر صفحهٔ پیش‌نویس روی نسخهٔ فعال اثر ندارد. فرم‌ها و مقاله‌ها طبق قرارداد فعلی منابع زندهٔ مستقل می‌مانند.
- تغییر قالب، صفحه‌های اضافه و لینک‌های معتبرشان را نگه می‌دارد و فقط محتوای اصلی را با رفتار فعلی بازنشانی می‌کند؛ لینک به بخش اصلی حذف‌شده پاک می‌شود.

## ترتیب اجرا

1. **قرارداد و سرور:** انواع مشترک، ساخت صفحهٔ اولیه بدون نظر مشتری ساختگی، نرمال‌سازی، پاک‌سازی ارجاع‌ها، اعتبارسنجی همهٔ صفحه‌ها/منوها، محدودیت تعداد و اندازه و آزمون انتشار و جداسازی مالک‌ها. چون داده در ستون‌های JSON موجود ذخیره می‌شود، migration پایگاه‌داده لازم نیست؛ دادهٔ قدیمی با فیلدهای اختیاری سازگار می‌ماند.
2. **وب عمومی:** مسیر صفحه، HTML قابل ایندکس، عنوان/توضیح/canonical مستقل، ناوبری مشترک دسکتاپ و گوشی، لینک کارت/دکمه و پشتیبانی proxy دامنهٔ تأییدشده. صفحهٔ غایب یا غیرفعال ۴۰۴ است.
3. **پنل وب:** بخش «صفحه‌ها و منوها»، ساخت/ویرایش/حذف/فعال‌سازی صفحه، انتخاب صفحه برای ویرایش بخش‌ها و پیش‌نمایش، تنظیم SEO، مدیریت ترتیب و مقصد منوها، انتخاب صفحهٔ داخلی برای کارت/دکمه و ساخت صفحه از آیتم خدمات. وضعیت ذخیره‌نشده و محافظ خروج روی کل سایت باقی می‌ماند.
4. **اپ مدیریت:** انتخاب صفحه و مدیریت تنظیمات و منوها، استفادهٔ مجدد از ویرایشگر بخش‌ها و اتصال کارت‌ها/دکمه‌ها به صفحه؛ ذخیره و انتشار همان قرارداد وب را اجرا می‌کند.
5. **یکپارچه‌سازی و مستندات:** اجرای بررسی‌های مخزن، آزمون واقعی مرورگر در عرض ۱۴۴۰ و ۳۶۰ و با صفحه‌کلید، ثبت نتیجه و محدودیت‌ها و به‌روزرسانی معماری و قرارداد API.

کارهای سرور، نمایش عمومی و اپ پس از تثبیت این قرارداد هم‌زمان اجرا می‌شوند؛ پنل وب و یکپارچه‌سازی در مسیر اصلی انجام می‌شود.

## معیار پذیرش

- مالک می‌تواند چند صفحهٔ عمومی/خدمت/موضوع بسازد، محتوا و SEO هرکدام را جدا ویرایش و همه را ذخیره و منتشر کند.
- تغییر پیش‌نویس، حذف صفحه، تغییر آدرس، منو و غیرفعال‌سازی تا انتشار دوباره اثری روی سایت زنده ندارد.
- لینک منو، کارت خدمت و دکمه به شناسهٔ صفحه متصل می‌شود و تغییر slug را دنبال می‌کند. ترتیب و محل نمایش منو قابل تغییر است؛ منوی گوشی با صفحه‌کلید باز و بسته می‌شود.
- سایت قدیمی، پیش‌نمایش قالب، فرم‌ها، بلاگ و پنل مخاطب سالم می‌مانند. صفحهٔ منتشرنشده از API و HTML عمومی قابل بازیابی نیست.
- API شناسه و آدرس تکراری، مقصد نامعتبر، ارجاع خارجی به صفحهٔ سایت دیگر و درخواست مالک دیگر/نشست مخاطب را رد می‌کند.
- `bun run db:generate`, `bun run db:deploy`, `bun run typecheck`, `bun run test`, `bun run build` و پس از تغییر اپ `bun run mobile:export` اجرا می‌شوند. export اپ به‌عنوان آزمون روی دستگاه گزارش نمی‌شود.

## خارج از این مرحله

صفحه‌های تو‌در‌تو، منوی چندسطحی، قالب جدا برای هر صفحه، انتشار مستقل یا زمان‌بندی‌شدهٔ هر صفحه، redirect تاریخچهٔ آدرس‌ها و کنترل تعارض ویرایش هم‌زمان. این موارد به مدل محصول و جریان مدیریت جدا نیاز دارند؛ اجرای کنونی برای سایت‌های کسب‌وکار با صفحه‌های هم‌سطح است.

## وضعیت اجرا

هر پنج مرحلهٔ برنامه اجرا شد: قرارداد و API، رندر عمومی و دامنه، پنل وب، اپ مدیریت و مستندات/بررسی‌ها. انواع جدید در JSON موجود ذخیره می‌شوند و تغییر schema لازم نبود.

۳۱ آزمون با ۲۴۰ بررسی موفق، typecheck همهٔ بسته‌ها، build وب و export اپ انجام شد. مرورگر در عرض ۱۴۴۰ و ۳۶۰ و با صفحه‌کلید بررسی شد. تاریخچهٔ migration پایگاه‌دادهٔ موجود از قبل ثبت نشده بود (`P3005`)؛ هر سه migration و آزمون‌های API در schema مستقل اجرا و آن schema پس از بررسی پاک شد. پایگاه‌دادهٔ کاربر بازنشانی نشد.
